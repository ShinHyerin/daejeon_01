How it works

팀이 굴러가는 네 가지 원리

서브에이전트는 부를 때마다 맥락 없이 새로 시작합니다. 그래서 호출 수가 곧 비용입니다. 효과가 큰 규칙만 남기고 호출은 꼭 필요한 곳에만 둡니다.

01

맥락은 이어 간다

기획부터 프론트·백엔드·테스트까지 메인이 한 맥락에서 진행합니다. API 계약을 양쪽이 같이 알고 있어야 하기 때문입니다.

예: API 응답 형식을 바꾸면 같은 맥락에서 프론트 타입도 바로 수정
02

남이 검토한다

작성 과정을 모르는 검수자를 새로 불러 diff를 봅니다. 작성자가 자기 코드를 검토하지 않습니다.

예: PR 리뷰어처럼 변경분과 테스트 결과만 받음
03

요구사항으로 이어진다

요구사항에 R1, R2 번호를 붙이고, 어떤 코드와 테스트로 충족됐는지 적습니다.

예: R1 → LoginForm.tsx:58 → test_login.py 통과
04

필요할 때만 부른다

요청 크기에 따라 경로가 달라집니다. 작은 수정에는 아무도 부르지 않습니다.

예: 오타 0회 · 기능 하나 1회 · 큰 작업 3회

Explore agent

탐색 에이전트는 언제 부르나

기준은 저장소 크기보다 관련 코드를 찾으려면 나중에 필요 없는 파일까지 많이 읽어야 하는가입니다.

불필요메인이 바로 찾는다

  • 파일 수십 개인 개인 프로젝트, 토이 앱
  • Next.js 블로그, 간단한 FastAPI 서버처럼 구조가 뻔한 프로젝트
  • "LoginForm.tsx에 비밀번호 확인 칸 추가"처럼 위치가 정해진 요청
  • 검색 한두 번으로 관련 파일이 나오는 경우

필요탐색 에이전트를 부른다

  • 파일 수백~수천 개인 모노레포 (apps/, packages/, services/)
  • "결제 실패하면 어디서 재시도하지?"처럼 흐름을 따라가야 하는 질문
  • 처음 받은 오픈소스나 남이 만든 레거시 코드
  • "이 함수를 바꾸면 영향받는 곳 전부"처럼 호출처가 흩어진 경우

메인이 직접 찾을 때

헛짚은 파일까지 메인 맥락에 계속 남음

탐색 에이전트를 쓸 때

메인에는 요약 한 줄과 필요한 파일만 들어옴
헛짚은 파일실제로 고칠 파일탐색 요약
간단한 기준: 검색 2~3번으로 위치가 안 나오면 탐색 에이전트를 부른다. 돌려받는 답 예시 → 재시도: services/payment/retry.ts:42 · 설정: config/queue.yaml
Cost

기능 하나를 만들 때의 호출 수

서브에이전트는 호출할 때마다 지침, 요구사항, 관련 파일을 다시 읽습니다. 호출 수가 줄면 같은 파일을 반복해서 읽는 비용도 줄어듭니다.

역할 분리형기획·프론트·백엔드·검수, 단계마다 검토
8회
세분화형기획·설계·UI·API·DB·테스트·문서·배포 8 + 단계 검토 7
15회
축소안 · 기능 하나메인 + 검수 1
1회
축소안 · 큰 작업탐색 1 + 검수 2
3회
작업 호출검토 호출탐색 호출
※ 막대 하나 = 30회 기준. 서브에이전트 호출 수만 센 개념 비교이며 실측 토큰이 아닙니다. 역할 분리형은 작업 4 + 검토 4로 가정했습니다.

Token saving

토큰을 아끼는 장치

구조를 줄인 다음, 남은 호출 하나하나를 가볍게 만듭니다.

검토는 되돌리기 비싼 곳에서만

기본은 구현 후 1번입니다. 큰 작업일 때만 설계 후에 1번 더 합니다.

보조 에이전트는 싼 모델로

탐색과 검수는 더 가벼운 모델로 돌립니다.

diff만 넘긴다

검수자에게 저장소 전체를 주지 않습니다. 요구사항, diff, 테스트 결과면 충분합니다.

재검수는 고친 부분만

지적받은 줄만 다시 보내고, 통과한 부분은 다시 보지 않습니다.

실패 로그만

테스트 로그는 전체 대신 실패한 부분만 넘깁니다.

돌려받는 답은 짧게

PR 설명처럼 변경 파일, 핵심 결정 3줄, 미해결 사항만 받습니다.
